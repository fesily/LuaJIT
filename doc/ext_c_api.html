LuaJIT adds some extensions to the standard Lua/C API. The LuaJIT include directory must be in the compiler search path (-Ipath) to be able to include the required header for C code: 

#include "luajit.h"

Or for C++ code: 

#include "lua.hpp"

luaJIT_setmode(L, idx, mode) — Control VM

This is a C API extension to allow control of the VM from C code. The full prototype of LuaJIT_setmode is: 

LUA_API int luaJIT_setmode(lua_State *L, int idx, int mode);

The returned status is either success (1) or failure (0). The second argument is either 0 or a stack index (similar to the other Lua/C API functions).

The third argument specifies the mode, which is 'or'ed with a flag. The flag can be LUAJIT_MODE_OFF to turn a feature off, LUAJIT_MODE_ON to turn a feature on, or LUAJIT_MODE_FLUSH to flush cached code.

The following modes are defined:

luaJIT_setmode(L, 0, LUAJIT_MODE_ENGINE|flag)

Turn the whole JIT compiler on or off or flush the whole cache of compiled code.

luaJIT_setmode(L, idx, LUAJIT_MODE_FUNC|flag)
luaJIT_setmode(L, idx, LUAJIT_MODE_ALLFUNC|flag)
luaJIT_setmode(L, idx, LUAJIT_MODE_ALLSUBFUNC|flag)

This sets the mode for the function at the stack index idx or the parent of the calling function (idx = 0). It either enables JIT compilation for a function, disables it and flushes any already compiled code, or only flushes already compiled code. This applies recursively to all sub-functions of the function with LUAJIT_MODE_ALLFUNC or only to the sub-functions with LUAJIT_MODE_ALLSUBFUNC.

luaJIT_setmode(L, trace,
  LUAJIT_MODE_TRACE|LUAJIT_MODE_FLUSH)

Flushes the specified root trace and all of its side traces from the cache. The code for the trace will be retained as long as there are any other traces which link to it.

luaJIT_setmode(L, idx, LUAJIT_MODE_WRAPCFUNC|flag)

This mode defines a wrapper function for calls to C functions. If called with LUAJIT_MODE_ON, the stack index at idx must be a lightuserdata object holding a pointer to the wrapper function. From now on, all C functions are called through the wrapper function. If called with LUAJIT_MODE_OFF this mode is turned off and all C functions are directly called.

The wrapper function can be used for debugging purposes or to catch and convert foreign exceptions. But please read the section on C++ exception interoperability first. Recommended usage can be seen in this C++ code excerpt: 

#include <exception>
#include "lua.hpp"

// Catch C++ exceptions and convert them to Lua error messages.
// Customize as needed for your own exception classes.
static int wrap_exceptions(lua_State *L, lua_CFunction f)
{
  try {
    return f(L);  // Call wrapped function and return result.
  } catch (const char *s) {  // Catch and convert exceptions.
    lua_pushstring(L, s);
  } catch (std::exception& e) {
    lua_pushstring(L, e.what());
  } catch (...) {
    lua_pushliteral(L, "caught (...)");
  }
  return lua_error(L);  // Rethrow as a Lua error.
}

static int myinit(lua_State *L)
{
  ...
  // Define wrapper function and enable it.
  lua_pushlightuserdata(L, (void *)wrap_exceptions);
  luaJIT_setmode(L, -1, LUAJIT_MODE_WRAPCFUNC|LUAJIT_MODE_ON);
  lua_pop(L, 1);
  ...
}

Note that you can only define a single global wrapper function, so be careful when using this mechanism from multiple C++ modules. Also note that this mechanism is not without overhead.

luaJIT_int3_* — One-shot interpreter interrupt

This C API extension arms a single, one-shot interrupt on one bytecode instruction of a Lua function and delivers a read-only native callback when that instruction is about to be executed. The full prototypes are: 

typedef void (*luaJIT_int3_callback)(void *data, lua_State *L,
                                     const void *proto, unsigned int bcpos);
LUA_API int luaJIT_int3_start(lua_State *L, luaJIT_int3_callback cb,
                              void *data);
LUA_API int luaJIT_int3_arm(lua_State *L, int func_index,
                            unsigned int bcpos);
LUA_API int luaJIT_int3_cancel(lua_State *L);
LUA_API int luaJIT_int3_stop(lua_State *L);

All calls must be made by the thread that owns the VM. At most one interrupt session can be active in the process and at most one request can be pending per VM.

luaJIT_int3_start starts a session for the VM of L. The JIT engine is left running and no trace is flushed; the session only records the callback and claims the process-wide profiler/interrupt slot. The function returns LUAJIT_INT3_UNAVAILABLE if profiling support is compiled out, LUAJIT_INT3_INVALID if cb is NULL, and LUAJIT_INT3_BUSY if machine code is executing, a GC, hook or VM event is active, or this or another VM already owns a profiler or interrupt session. Nothing is changed when the call is refused.

luaJIT_int3_arm replaces the opcode of the instruction at bcpos (a 0-based bytecode index, bcpos < sizebc) in the prototype of the Lua function at stack index func_index by BC_INT3. The other operand fields, PC, jump offsets and line numbers stay intact, and the prototype is kept alive.

Only the traces that can reach this bytecode are dropped: a trace is flushed if it starts in the prototype, if it inlined it (the recorder specializes every recorded Lua call on a GC constant for the prototype or for one of its closures), or if one of its snapshots points into the prototype. All other traces keep running, and the JIT stays enabled. To keep the bytecode interpreted for the duration of the request, the prototype is excluded from JIT compilation: no new trace may start in it or inline it, so callers that call it fall back to the interpreter (their recording is aborted, exactly like jit.off(func)). Enabling JIT compilation for that prototype (or for a subtree containing it) through luaJIT_setmode is refused until the request is gone.

The function returns LUAJIT_INT3_OK, LUAJIT_INT3_DISABLED if no session is owned by this VM, LUAJIT_INT3_BUSY if a request is already pending, the recorder is active, machine code is executing or the context is unsafe, or LUAJIT_INT3_INVALID for a non-Lua function or an out-of-range bcpos.

The callback is invoked exactly once, when the interpreter dispatches the trapped instruction. The request is consumed before the callback runs, the original instruction is restored, and it then executes normally. Repeating the call site does not invoke the callback again until luaJIT_int3_arm is called again. The callback receives the prototype as an opaque identity pointer that is only valid for the duration of the call, and bcpos as the index of the original instruction in that prototype. The interpreter state (lua_State, current frame, PC, top) is consistent and read-only.

The callback must not run Lua code, yield, raise or catch errors, call luaJIT_int3_*, flush traces, change hook or JIT state, or trigger a GC. It may only inspect the VM.

luaJIT_int3_cancel restores the original instruction and drops a pending request, which also makes the prototype compilable again. The session itself stays open. It returns LUAJIT_INT3_OK if nothing is pending.

luaJIT_int3_stop cancels a pending request and releases the session. The engine on/off state is not touched: if the JIT was enabled it stays enabled, and traces recorded earlier keep running. A VM that is closed while a request is pending drops it without invoking the callback.
