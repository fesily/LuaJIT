LuaJIT adds some extensions to the standard Lua/C API. The LuaJIT include directory must be in the compiler search path (-Ipath) to be able to include the required header for C code: 

#include "luajit.h"

Or for C++ code: 

#include "lua.hpp"

luaJIT_setmode(L, idx, mode) — Control VM

This is a C API extension to allow control of the VM from C code. The full prototype of LuaJIT_setmode is: 

LUA_API int luaJIT_setmode(lua_State *L, int idx, int mode);

The returned status is either success (1) or failure (0). The second argument is either 0 or a stack index (similar to the other Lua/C API functions).

The third argument specifies the mode, which is 'or'ed with a flag. The flag can be LUAJIT_MODE_OFF to turn a feature off, LUAJIT_MODE_ON to turn a feature on, or LUAJIT_MODE_FLUSH to flush cached code.

The following modes are defined:

luaJIT_setmode(L, 0, LUAJIT_MODE_ENGINE|flag)

Turn the whole JIT compiler on or off or flush the whole cache of compiled code.

luaJIT_setmode(L, idx, LUAJIT_MODE_FUNC|flag)
luaJIT_setmode(L, idx, LUAJIT_MODE_ALLFUNC|flag)
luaJIT_setmode(L, idx, LUAJIT_MODE_ALLSUBFUNC|flag)

This sets the mode for the function at the stack index idx or the parent of the calling function (idx = 0). It either enables JIT compilation for a function, disables it and flushes any already compiled code, or only flushes already compiled code. This applies recursively to all sub-functions of the function with LUAJIT_MODE_ALLFUNC or only to the sub-functions with LUAJIT_MODE_ALLSUBFUNC.

luaJIT_setmode(L, trace,
  LUAJIT_MODE_TRACE|LUAJIT_MODE_FLUSH)

Flushes the specified root trace and all of its side traces from the cache. The code for the trace will be retained as long as there are any other traces which link to it.

luaJIT_setmode(L, idx, LUAJIT_MODE_WRAPCFUNC|flag)

This mode defines a wrapper function for calls to C functions. If called with LUAJIT_MODE_ON, the stack index at idx must be a lightuserdata object holding a pointer to the wrapper function. From now on, all C functions are called through the wrapper function. If called with LUAJIT_MODE_OFF this mode is turned off and all C functions are directly called.

The wrapper function can be used for debugging purposes or to catch and convert foreign exceptions. But please read the section on C++ exception interoperability first. Recommended usage can be seen in this C++ code excerpt: 

#include <exception>
#include "lua.hpp"

// Catch C++ exceptions and convert them to Lua error messages.
// Customize as needed for your own exception classes.
static int wrap_exceptions(lua_State *L, lua_CFunction f)
{
  try {
    return f(L);  // Call wrapped function and return result.
  } catch (const char *s) {  // Catch and convert exceptions.
    lua_pushstring(L, s);
  } catch (std::exception& e) {
    lua_pushstring(L, e.what());
  } catch (...) {
    lua_pushliteral(L, "caught (...)");
  }
  return lua_error(L);  // Rethrow as a Lua error.
}

static int myinit(lua_State *L)
{
  ...
  // Define wrapper function and enable it.
  lua_pushlightuserdata(L, (void *)wrap_exceptions);
  luaJIT_setmode(L, -1, LUAJIT_MODE_WRAPCFUNC|LUAJIT_MODE_ON);
  lua_pop(L, 1);
  ...
}

Note that you can only define a single global wrapper function, so be careful when using this mechanism from multiple C++ modules. Also note that this mechanism is not without overhead.

luaJIT_int3_* — Interpreter breakpoints

This C API extension turns bytecode instructions of Lua functions into breakpoints: an armed instruction delivers a read-only native callback on every execution, before it runs. The full prototypes are: 

typedef void (*luaJIT_int3_callback)(void *data, lua_State *L,
                                     const void *func, unsigned int bcpos);
LUA_API int luaJIT_int3_start(lua_State *L, luaJIT_int3_callback cb,
                              void *data);
LUA_API int luaJIT_int3_arm(lua_State *L, int func_index,
                            unsigned int line);
LUA_API int luaJIT_int3_arm_bc(lua_State *L, int func_index,
                               unsigned int bcpos);
LUA_API int luaJIT_int3_cancel(lua_State *L);
LUA_API int luaJIT_int3_stop(lua_State *L);

All calls must be made by the thread that owns the VM. A session belongs to the VM that started it (it is allocated from that VM's allocator and released by luaJIT_int3_stop or, at the latest, when the VM is closed), but at most one breakpoint session can be active in the process, and at most LJ_INT3_MAX (32) breakpoints can be armed at the same time, each on one bytecode slot and in any mix of prototypes: several slots of one prototype and slots of different prototypes can be armed together. Arming a slot that is already armed is a no-op and returns LUAJIT_INT3_OK.

A breakpoint is permanent. It keeps its slot, its callback, its prototype GC root and the JIT exclusion until it is disarmed by luaJIT_int3_cancel, by luaJIT_int3_stop or by closing the VM. Hits do not consume the breakpoint and do not free its capacity: a debugger that wants a limited number of hits counts them in the callback and cancels or stops the session when it is done.

luaJIT_int3_start starts a session for the VM of L. The JIT engine is left running and no trace is flushed; the session only records the callback and claims the process-wide profiler/breakpoint slot. The function returns LUAJIT_INT3_UNAVAILABLE if profiling support is compiled out, LUAJIT_INT3_INVALID if cb is NULL, and LUAJIT_INT3_BUSY if machine code is executing, a GC, hook or VM event is active, or this or another VM already owns a profiler or breakpoint session. Nothing is changed when the call is refused.

luaJIT_int3_arm arms the first breakpoint slot of source line line (1-based, as the debug interface reports it) of the Lua function at stack index func_index, and luaJIT_int3_arm_bc arms the bytecode slot at bcpos (0-based, bcpos < sizebc), i.e. the (func, bcpos) identity the callback reports. Either way the slot's opcode becomes BC_INT3; the other operand fields, PC, jump offsets and line numbers stay intact, and the prototype is kept alive.

The line entry point resolves the first slot of that line that can carry a trap, in bytecode order, starting after the function header (it shares the line of the first body statement and is never a slot): instructions that cannot be trapped are skipped, so a one-line loop still yields a slot, and a line without one returns LUAJIT_INT3_NOTFOUND. A prototype with no line information (a stripped bytecode chunk) reports line 0 for every slot: line 0 is not a source line, so such a request also returns LUAJIT_INT3_NOTFOUND and arms nothing; luaJIT_int3_arm_bc still works for those chunks. A debugger that needs an exact slot, or that maps its breakpoints itself (the slot numbering of a prototype follows from its bytecode, so code minified onto a single line cannot be addressed by line alone), uses luaJIT_int3_arm_bc.

Arming is asynchronous: LUAJIT_INT3_OK means that the request was accepted, not that the slot already holds the trap. A call from the host, from a C function or from the breakpoint callback mounts the request before returning. A call from a Lua debug hook or from the recorder/compiler only queues it: replacing the slot there would race the dispatch or the bytecode patch in progress, and flushing would drop the trace that is being recorded. The next dispatch mounts every queued request at a safe point, after the hook and recorder work and before the next instruction executes. A queued request already holds its GC root and forces the C dispatch, so it can neither be lost nor be observed as armed before it is; the JIT may still compile the prototype until then.

Mounting a breakpoint drops only the traces that can reach this bytecode: a trace is flushed if it starts in the prototype, if it inlined it (the recorder specializes every recorded Lua call on a GC constant for the prototype or for one of its closures), or if one of its snapshots points into the prototype. All other traces keep running, and the JIT stays enabled. To keep the bytecode interpreted for as long as the prototype carries a breakpoint, the prototype is excluded from JIT compilation: no new trace may start in it or inline it, so callers that call it fall back to the interpreter (their recording is aborted, exactly like jit.off(func)). Tracing stops right away, not lazily: the hot counters of the prototype keep running, but the recorder is never entered for it (or for a caller that could inline it), so no bytecode patch is ever applied to it while a breakpoint exists. Enabling JIT compilation for that prototype (or for a subtree containing it) through luaJIT_setmode is refused until the last breakpoint of that prototype is gone.

A prototype that the host disabled with jit.off keeps that state across the breakpoint: the exclusion is only released when the breakpoint itself added it. This holds whether compilation was disabled before the request was armed or while the prototype already carried the breakpoint.

Only the slots the interpreter never dispatches on its own are refused with LUAJIT_INT3_UNARMABLE: function headers (FUNCF/FUNCV, including their patched forms, whose frame is not set up when they run) and the generic-for prep pair (ISNEXT and the ITERN slot it points at, which the prep slot rewrites when it despecializes). A JMP slot that the preceding comparison or test (ISLT..ISF) consumes is refused as well: the comparison branches over that slot, so it is never dispatched on its own and a trap there could never fire.

Every other slot is a breakpoint site, including the loop instructions (FORI, FORL, ITERL, LOOP), a loop back edge and RET/RET0/RET1/RETM. That is safe because arming flushes the traces that can reach the prototype and excludes it from JIT compilation for as long as it carries a breakpoint: no trace of it exists then, so the tracer can never rewrite an armed loop, prep or return slot. A slot that was traced or lazily blacklisted is rewritten back to its plain form when the request is mounted, and the trap is planted on that plain instruction; the reverse patch happens only after the last request is cancelled.

The function returns LUAJIT_INT3_OK (accepted, mounted now or at the next safe point), LUAJIT_INT3_DISABLED if no session is owned by this VM, LUAJIT_INT3_BUSY if a GC, a foreign VM event, the profiler or machine code is executing, LUAJIT_INT3_FULL if all LJ_INT3_MAX breakpoint slots are in use, LUAJIT_INT3_UNARMABLE for a function header, a generic-for prep slot or a paired jump slot, or LUAJIT_INT3_INVALID for a non-Lua function or an out-of-range bcpos. It may also be called from the breakpoint callback, which then arms another slot (or re-arms the slot that is being delivered) while the current hit is being delivered.

luaJIT_int3_arm may also be called from a Lua debug hook (lua_sethook) and from a recorder or trace callback. Inside a hook the request is queued and mounted at the end of that dispatch, so the instruction the hook belongs to still executes with its own opcode exactly once. The breakpoint then fires from the next dispatch of that slot on: arming the current slot does not deliver a callback for the execution that is already being dispatched, while arming a later slot (or the body of a callee from a call hook, which mounts at the call dispatch) fires as soon as execution reaches it. luaJIT_int3_start, luaJIT_int3_cancel and luaJIT_int3_stop are accepted from a Lua debug hook as well: that hook's own dispatch re-reads every slot they touch, so a restored slot simply runs its instruction, and a request armed above mounts at the same safe point. A trap is delivered on the dispatch of its own slot, which happens before the line or count hook of that instruction, so a hook that cancels or stops takes effect from the next dispatch on and cannot suppress a callback that already ran, while a slot the hook runs before is preempted. The GC, profiler, foreign VM event and machine-code/recorder/compiler contexts still refuse every call with LUAJIT_INT3_BUSY.

The callback is invoked once for every execution of the armed instruction, before that instruction runs. The breakpoint stays armed, so the next execution delivers the next hit. The instruction that was trapped is the one that executes, exactly once, with its original opcode, operands, debug hooks and metamethod/global lookup paths: arming a slot never changes the result or the side effects of the program. Line, count, call and return hooks observe the instruction normally.

The callback receives func, the running closure as an opaque identity pointer (the same value lua_topointer returns for that function, i.e. its GCfunc *), and bcpos as the index of the original instruction in its prototype. Two closures of one prototype are therefore distinguishable, and the closure is what a debugger needs to read upvalues or the environment without reconstructing the frame; the pointer is only valid for the duration of the call. The interpreter state (lua_State, current frame, PC, top) is consistent and read-only.

The callback must not run Lua code, yield, raise or catch errors, flush traces, change hook or JIT state, or trigger a GC. It may inspect the VM and it may call luaJIT_int3_arm, luaJIT_int3_cancel and luaJIT_int3_stop: the delivery context is safe for these calls, and every other context rule still applies. A callback that cancels or stops the session disarms the slot it is delivering, and that execution still runs the original instruction: the hit is delivered, not consumed mid-instruction.

luaJIT_int3_cancel restores the original instructions and disarms all breakpoints, which also makes the prototypes compilable again. The session itself stays open, so new breakpoints can be armed afterwards. It returns LUAJIT_INT3_OK if nothing is armed.

luaJIT_int3_stop disarms all breakpoints and releases the session. The engine on/off state is not touched: if the JIT was enabled it stays enabled, and traces recorded earlier keep running. A VM that is closed while breakpoints are armed restores them without invoking the callback.

A breakpoint keeps trapping until it is disarmed. Counting hits in the callback and disarming the session when the limit is reached is therefore: 

static void on_hit(void *data, lua_State *L, const void *func,
                   unsigned int bcpos)
{
  if (++hits >= limit)
    luaJIT_int3_cancel(L);  /* Or luaJIT_int3_stop(L). */
}
