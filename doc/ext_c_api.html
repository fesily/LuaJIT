LuaJIT adds some extensions to the standard Lua/C API. The LuaJIT include directory must be in the compiler search path (-Ipath) to be able to include the required header for C code: 

#include "luajit.h"

Or for C++ code: 

#include "lua.hpp"

luaJIT_setmode(L, idx, mode) — Control VM

This is a C API extension to allow control of the VM from C code. The full prototype of LuaJIT_setmode is: 

LUA_API int luaJIT_setmode(lua_State *L, int idx, int mode);

The returned status is either success (1) or failure (0). The second argument is either 0 or a stack index (similar to the other Lua/C API functions).

The third argument specifies the mode, which is 'or'ed with a flag. The flag can be LUAJIT_MODE_OFF to turn a feature off, LUAJIT_MODE_ON to turn a feature on, or LUAJIT_MODE_FLUSH to flush cached code.

The following modes are defined:

luaJIT_setmode(L, 0, LUAJIT_MODE_ENGINE|flag)

Turn the whole JIT compiler on or off or flush the whole cache of compiled code.

luaJIT_setmode(L, idx, LUAJIT_MODE_FUNC|flag)
luaJIT_setmode(L, idx, LUAJIT_MODE_ALLFUNC|flag)
luaJIT_setmode(L, idx, LUAJIT_MODE_ALLSUBFUNC|flag)

This sets the mode for the function at the stack index idx or the parent of the calling function (idx = 0). It either enables JIT compilation for a function, disables it and flushes any already compiled code, or only flushes already compiled code. This applies recursively to all sub-functions of the function with LUAJIT_MODE_ALLFUNC or only to the sub-functions with LUAJIT_MODE_ALLSUBFUNC.

luaJIT_setmode(L, trace,
  LUAJIT_MODE_TRACE|LUAJIT_MODE_FLUSH)

Flushes the specified root trace and all of its side traces from the cache. The code for the trace will be retained as long as there are any other traces which link to it.

luaJIT_setmode(L, idx, LUAJIT_MODE_WRAPCFUNC|flag)

This mode defines a wrapper function for calls to C functions. If called with LUAJIT_MODE_ON, the stack index at idx must be a lightuserdata object holding a pointer to the wrapper function. From now on, all C functions are called through the wrapper function. If called with LUAJIT_MODE_OFF this mode is turned off and all C functions are directly called.

The wrapper function can be used for debugging purposes or to catch and convert foreign exceptions. But please read the section on C++ exception interoperability first. Recommended usage can be seen in this C++ code excerpt: 

#include <exception>
#include "lua.hpp"

// Catch C++ exceptions and convert them to Lua error messages.
// Customize as needed for your own exception classes.
static int wrap_exceptions(lua_State *L, lua_CFunction f)
{
  try {
    return f(L);  // Call wrapped function and return result.
  } catch (const char *s) {  // Catch and convert exceptions.
    lua_pushstring(L, s);
  } catch (std::exception& e) {
    lua_pushstring(L, e.what());
  } catch (...) {
    lua_pushliteral(L, "caught (...)");
  }
  return lua_error(L);  // Rethrow as a Lua error.
}

static int myinit(lua_State *L)
{
  ...
  // Define wrapper function and enable it.
  lua_pushlightuserdata(L, (void *)wrap_exceptions);
  luaJIT_setmode(L, -1, LUAJIT_MODE_WRAPCFUNC|LUAJIT_MODE_ON);
  lua_pop(L, 1);
  ...
}

Note that you can only define a single global wrapper function, so be careful when using this mechanism from multiple C++ modules. Also note that this mechanism is not without overhead.

luaJIT_int3_* — Interpreter breakpoints

This C API extension turns bytecode instructions of Lua functions into breakpoints: an armed instruction delivers a read-only native callback on every execution, before it runs. The full prototypes are: 

typedef void (*luaJIT_int3_callback)(void *data, lua_State *L,
                                     const void *proto, unsigned int bcpos);
LUA_API int luaJIT_int3_start(lua_State *L, luaJIT_int3_callback cb,
                              void *data);
LUA_API int luaJIT_int3_arm(lua_State *L, int func_index,
                            unsigned int bcpos);
LUA_API int luaJIT_int3_cancel(lua_State *L);
LUA_API int luaJIT_int3_stop(lua_State *L);

All calls must be made by the thread that owns the VM. At most one breakpoint session can be active in the process, and at most LJ_INT3_MAX (32) breakpoints can be armed at the same time, each on one bytecode slot and in any mix of prototypes: several slots of one prototype and slots of different prototypes can be armed together. Arming a slot that is already armed is a no-op and returns LUAJIT_INT3_OK.

A breakpoint is permanent. It keeps its slot, its callback, its prototype GC root and the JIT exclusion until it is disarmed by luaJIT_int3_cancel, by luaJIT_int3_stop or by closing the VM. Hits do not consume the breakpoint and do not free its capacity: a debugger that wants a limited number of hits counts them in the callback and cancels or stops the session when it is done.

luaJIT_int3_start starts a session for the VM of L. The JIT engine is left running and no trace is flushed; the session only records the callback and claims the process-wide profiler/breakpoint slot. The function returns LUAJIT_INT3_UNAVAILABLE if profiling support is compiled out, LUAJIT_INT3_INVALID if cb is NULL, and LUAJIT_INT3_BUSY if machine code is executing, a GC, hook or VM event is active, or this or another VM already owns a profiler or breakpoint session. Nothing is changed when the call is refused.

luaJIT_int3_arm arms the instruction at bcpos (a 0-based bytecode index, bcpos < sizebc) in the prototype of the Lua function at stack index func_index and keeps the prototype alive. The canonical bytecode array is never modified. The VM keeps one shadow copy of the complete bytecode of a prototype; only the shadow slot holds BC_INT3 (with the original operands), and only a new instruction fetch reads the shadow. Every hook, recorder and slow-path re-read of the bytecode keeps reading the canonical array, so jit.util.funcbc, dumps, debug line numbers and tracebacks always see the real program, and no other module has to translate a trapped slot.

The request is mounted automatically at the next safe point: the prototype is kept out of the JIT (as jit.off(func) does) and its shadow is created. LUAJIT_INT3_OK means the request was accepted, not that it is already mounted. A host call and the breakpoint callback mount it before returning. A Lua debug hook and the recorder/compiler only register it: they force the interpreter through the C dispatch, which mounts it at the next instruction or call boundary. The instruction the hook belongs to is fetched from the canonical array, so it still executes with its own opcode exactly once, and the breakpoint fires from the next fetch of that slot on.

When a request is mounted, only the traces that can reach this bytecode are dropped: a trace is flushed if it starts in the prototype, if it inlined it (the recorder specializes every recorded Lua call on a GC constant for the prototype or for one of its closures), or if one of its snapshots points into the prototype. All other traces keep running, and the JIT stays enabled. To keep the bytecode interpreted for as long as the prototype carries a breakpoint, the prototype is excluded from JIT compilation: no new trace may start in it or inline it, so callers that call it fall back to the interpreter (their recording is aborted, exactly like jit.off(func)). Tracing stops right away, not lazily: the hot counters of the prototype keep running, but the recorder is never entered for it (or for a caller that could inline it), so no bytecode patch is ever applied to it while a breakpoint exists. Enabling JIT compilation for that prototype (or for a subtree containing it) through luaJIT_setmode is refused until the last breakpoint of that prototype is gone.

Only slots that the JIT does not rewrite at run time can be armed: function headers (FUNCF/FUNCV), the loop instructions (FORI, FORL, ITERL, LOOP), the generic-for slots (ITERN/ISNEXT) and RET/RET0/RET1 are refused with LUAJIT_INT3_UNARMABLE. RETM is not rewritten by the tracer and can be armed. Arm the first instruction of the function body or of the loop body instead: it delivers the same events and cannot race with a bytecode patch.

The function returns LUAJIT_INT3_OK, LUAJIT_INT3_DISABLED if no session is owned by this VM, LUAJIT_INT3_BUSY if machine code is executing, a GC, a foreign VM event or a profiler is active, or the context is otherwise unsafe, LUAJIT_INT3_FULL if all LJ_INT3_MAX breakpoint slots are in use, LUAJIT_INT3_UNARMABLE for a slot the JIT rewrites at run time, LUAJIT_INT3_NOMEM if the shadow of the prototype cannot be allocated (the request is not established and nothing is changed), or LUAJIT_INT3_INVALID for a non-Lua function or an out-of-range bcpos. It may also be called from the breakpoint callback, which then arms another slot (or re-arms the slot that is being delivered) while the current hit is being delivered, and from the recorder/compiler, where it is only registered for the next safe point.

luaJIT_int3_arm may also be called from a Lua debug hook (lua_sethook). Inside a hook the request is registered as pending and mounted at the return of that dispatch: the instruction the hook belongs to still executes with its own opcode exactly once, because it is re-dispatched from the canonical array, and the breakpoint fires from the next fetch of that slot on. Arming the current slot therefore does not deliver a callback for the execution that is already being dispatched, while arming a later slot (or the body of a callee from a call hook) fires as soon as execution reaches it. Every other call (luaJIT_int3_start, luaJIT_int3_cancel, luaJIT_int3_stop) is still refused with LUAJIT_INT3_BUSY inside a hook, as are the GC, foreign VM event, profiler and machine-code contexts.

While a request is pending, the instruction dispatcher temporarily routes every instruction through the C dispatch, so the next safe point is reached without a per-instruction poll. No user hook is installed or replaced, and the original dispatch table is restored as soon as the request is mounted.

The callback is invoked once for every new fetch of the armed instruction, before that instruction runs. The breakpoint stays armed, so the next fetch delivers the next hit. The instruction that was trapped is the one that executes, exactly once, with its original opcode, operands, debug hooks and metamethod/global lookup paths: arming a slot never changes the result or the side effects of the program. Line, count, call and return hooks observe the instruction normally.

The callback receives the prototype as an opaque identity pointer that is only valid for the duration of the call, and bcpos as the index of the original instruction in that prototype. The interpreter state (lua_State, current frame, PC, top) is consistent and read-only.

The callback must not run Lua code, yield, raise or catch errors, flush traces, change hook or JIT state, or trigger a GC. It may inspect the VM and it may call luaJIT_int3_arm, luaJIT_int3_cancel and luaJIT_int3_stop: the delivery context is safe for these calls, and every other context rule still applies. A callback that cancels or stops the session disarms the slot it is delivering, and that execution still runs the original instruction: the hit is delivered, not consumed mid-instruction.

luaJIT_int3_cancel withdraws the shadow mappings, releases the shadow memory and disarms all breakpoints, which also makes the prototypes compilable again (a jit.off(func) the caller had applied itself is kept). The session itself stays open, so new breakpoints can be armed afterwards. It returns LUAJIT_INT3_OK if nothing is armed.

luaJIT_int3_stop disarms all breakpoints, releases their shadows and releases the session. The engine on/off state is not touched: if the JIT was enabled it stays enabled, and traces recorded earlier keep running. A VM that is closed while breakpoints are armed releases them without invoking the callback.

A breakpoint keeps trapping until it is disarmed. Counting hits in the callback and disarming the session when the limit is reached is therefore: 

static void on_hit(void *data, lua_State *L, const void *proto,
                   unsigned int bcpos)
{
  if (++hits >= limit)
    luaJIT_int3_cancel(L);  /* Or luaJIT_int3_stop(L). */
}
